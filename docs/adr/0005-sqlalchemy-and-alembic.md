# 5. SQLAlchemy and Alembic for data access
Status: Accepted. Supersedes the "raw SQL in repositories and no ORM" part of ADR 0001.

## Context
ADR 0001 chose raw SQL through psycopg 3. In practice each table is described three times: in a SQL migration, in a row dataclass, and in a column list inside the repository. They are kept in sync by hand, and a mismatch only shows up as a runtime error in tests. The schema is still small (two migrations, three repositories with real queries), so changing approach now is cheap; it gets more expensive with every issue that adds tables.

The workload is Postgres-specific: a `SELECT ... FOR UPDATE SKIP LOCKED` job queue, pgvector similarity search, `INSERT ... ON CONFLICT` upserts, advisory locks, and `LISTEN/NOTIFY`. Whatever replaces raw SQL has to express these without fighting the tool.

## Decision
Use SQLAlchemy 2.0 (async) on the psycopg 3 driver, with Alembic for migrations.

1. **Models are the schema.** Declarative `Mapped[...]` models in `src/curio/db/models/`, one module per domain (e.g. `users.py`, `keys.py`), are the single definition of every table.
2. **Alembic replaces the hand-written SQL migrations.** Revisions are autogenerated from the models and reviewed before committing; autogenerate is a starting point, not the final word. The `migrate` service runs `alembic upgrade head`, still under a Postgres advisory lock so concurrent runs serialise. The app never migrates on startup.
3. **Repositories stay.** All database access still lives in `repositories/`, written as 2.0-style `select()` / `insert()` / `update()` statements. Every per-user function still takes `user_id` as a required argument. Postgres-specific features use SQLAlchemy's Postgres dialect (`with_for_update(skip_locked=True)`, `postgresql.insert().on_conflict_do_update()`, pgvector's `Vector` type); `text()` is allowed for the rest (advisory locks, `LISTEN/NOTIFY`).
4. **No implicit I/O.** Relationships use `lazy="raise"` and load explicitly (`selectinload`, joins). Sessions use `expire_on_commit=False`. Under async, any lazy load would be an error or a hidden query, so none are allowed.
5. **Transactions.** A request-scoped `AsyncSession` replaces the request-scoped connection: it commits on success and rolls back on error. Code that needs an explicit transaction uses `session.begin_nested()` or a fresh session, never `commit()` inside a repository. Work that must survive the caller's rollback (the decrypt audit log, ADR 0002) uses its own session from the session factory and commits it independently.
6. **ORM models never reach an HTTP response.** Routes map models to Pydantic schemas in `api/schemas/<domain>.py` explicitly. An ORM model carries every column (for example `encrypted_key` on the API key model), so returning one directly is how secrets leak into responses or the OpenAPI schema. Repositories that serve display paths select only the columns they need.

## Alternatives considered
- **Keep raw SQL with psycopg (ADR 0001).** Explicit and dependency-light, but the triple definition of each table stays manual, and dynamic filtering (e.g. the Agent Traces tab) needs hand-built SQL strings.
- **SQLAlchemy Core only, no ORM.** Gives the query builder and `Table` metadata, but not mapped classes, and Alembic autogenerate works equally well with either. Mapped classes give typed rows for free, so the ORM's declarative layer is worth it as long as rule 4 keeps its runtime behaviour predictable.
- **SQLModel.** Merges ORM models and API schemas into one class, which is exactly the coupling rule 6 forbids.

## Consequences
- One definition per table; schema drift between models and migrations is caught by `alembic check` in CI.
- The test fixtures change: each test joins a SQLAlchemy session to an outer transaction that is rolled back afterwards (SQLAlchemy's "join a session into an external transaction" pattern), so test isolation still holds.
- The existing SQL migrations `0001` and `0002` become the initial Alembic revision. Any database created by the old runner needs `alembic stamp` once; the migration issue documents this.
- New dependencies: `sqlalchemy[asyncio]`, `alembic`, and `pgvector` (for its SQLAlchemy type).
- Reviewers should read the SQL the ORM emits for non-trivial queries (`echo=True` in development) rather than trust it blindly.
